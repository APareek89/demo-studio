# FMEA — optional local LiveKit transport trial

Review date: 25 September 2026. Scope: the new `server/livekit_trial.py`, `web/player/livekit-voice.js`, `scripts/run_livekit_trial.py`, `scripts/livekit_trial_server.py`, their application/player entrypoints, optional dependency pins and vendored SDK provenance, and the focused contracts. The vendor implementation was checked at the SDK interfaces used here; this is not a complete upstream security audit. The companion [acceptance receipt](README.md) records the final test revision and counts.

Product context: `PRD.md` requires interruption without lost speech, one selected voice, source-grounded answers, image-before-speech, preserved return points and incrementally saved visits. The approved plan in `refine.MD` limits this package to a local, opt-in transport trial. Build, Align, reasoning/provider order, reviewed images, gallery geometry and publication rules remain unchanged. The baseline EC2 instance is small and is not a deployment target for this trial.

The trial carries microphone audio over a real WebRTC track. Existing session controls and bounded PCM output use LiveKit reliable data; prerecorded clips remain HTTP. Client qualification and playback retain semantic ownership. LiveKit Agents automatic turns, noise isolation and outbound RTP speech are not implemented or claimed.

Network boundary: the app, token endpoint and LiveKit signalling bind to loopback. RTC UDP binds to one explicitly selected private IPv4 address owned by this machine, restricted to that address's `/32`; it is not a loopback listener. The launcher validates ownership with a local bind probe. Native libwebrtc did not offer a usable loopback candidate in three real connection probes, so an all-loopback media configuration was rejected. TCP media is disabled, public STUN is replaced with explicit local settings, and all trial participants still need scoped credentials. This is a same-machine RTC trial, not an Internet deployment or a system-wide firewall.

These are concrete initial-draft defects found before trial acceptance. Scores describe the original exposure, not a remaining defect. S/O/D use the repository's 1–10 anchors; RPN is their product; P0 starts at 200 and P1 at 100.

Bounded readiness-only retries cover data-channel activation. Duplicate ready controls cannot replay `session.start` or a customer question; reconnect still closes the trial. |

The initial empty-ICE interpretation was disproved by the installed Python SDK and pinned server source. `RtcConfiguration.ice_servers=[]` inherits SFU settings; LiveKit Server v1.13.7 substitutes public STUN defaults when its list is empty. The RTC TCP bind behavior was also confirmed in the pinned transport library. These checks are why configuration-only mock assertions cannot establish network isolation. Sources: [server room-manager defaults](https://github.com/livekit/livekit/blob/v1.13.7/pkg/service/roommanager.go), [pinned RTC configuration](https://github.com/livekit/mediatransportutil/blob/f234b534b095/pkg/rtcconfig/config.go), [pinned RTC listener implementation](https://github.com/livekit/mediatransportutil/blob/f234b534b095/pkg/rtcconfig/webrtc_config.go).

Real connection evidence then exposed LK-10/LK-11: data-only, publishing-enabled and single-peer-connection loopback probes each timed out. With the selected private host address, the worker joined in 0.259 seconds and negotiated DTLS on a same-host UDP candidate pair. This proves that connection path only; it does not establish voice quality, end-to-end response latency or public-network recovery. Failed probes remain part of the acceptance evidence.

Both a real Python viewer and the browser then reproduced LK-12 despite connected ICE/DTLS. The fix preserves sender ownership rather than accepting an unattributed packet or retrying a semantic turn. The readiness exchange has its own client deadline, accepts only the assigned worker/topic/session, and is cancelled on close. The worker sends at most four readiness invitations at half-second intervals. A participant that becomes data-active after that budget receives a visible connection failure and can explicitly retry; this trial does not extend or silently replay the semantic session. Mock SDK event order alone would not have exposed this failure; the actual RTC acceptance receipt is required.

|---|---|---|

| `external_dependency_failures` | Missing optional SDK, absent SFU, broken STT/TTS and RTC disconnection | Normal application import does not require LiveKit. | `race_conditions_and_state` | Track/data arrival order, participant visibility, rapid mute/unmute, late ready/final frames, reconnect and answer output | Exact room participant, input generation, capture epoch, turn and utterance ownership. | `resource_exhaustion` | Room reservations, incoming PCM/control queues, fragmentation and body parsing | Four reserved bridges, including pending native cleanup; independent join, idle and visit limits; bounded queues, fragment count/message size/concurrency/expiry; preserved eight-second prebuffer with visible overflow failure. Corrected LK-03/LK-08/LK-11. A stuck native operation keeps its slot unavailable rather than allowing unbounded retries; the owned process can be restarted. This is not a public load test. |

| `observability_gaps` | Failed worker versus connected microphone; proof of actual audio transport | Specific trial errors, owned local process logs, ping/pong and received/forwarded RTC frame counters. | `billing_credit_mismatches` | Trial launch and reconnect around provider work | Launcher defaults to MOCK_LLM with provider keys cleared and the mock socket guard enabled; live-provider mode is an explicit operator choice. | `retry_idempotency_issues` | Duplicate fragments, readiness invitation, reconnect and a second question | Completed-message deduplication and existing turn/utterance ownership; readiness retries carry no semantic request and stop when the owned session starts. | `edge_cases_from_prd` | Noise hold, unfinished question, known control, shown picture, Continue and saved visit | Inherit the tested player/runtime behavior rather than adding a second conversational agent. Actual RTC integration must exercise these paths with the approved BMW copy. A synthetic microphone cannot prove throat-clearing rejection, speaker identity, echo handling or acoustic quality. |

**Coverage: 12/12 categories checked.** No additional open correctness defect was identified in data-write semantics or model/grounding ownership. No new billing flow, approval flow or graph node was introduced. Corrected findings require their regression checks in the companion receipt; this document is not a substitute for those results.
