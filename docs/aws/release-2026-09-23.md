## Rollback

Rollback was prepared and reviewed, not executed. It removes only the new service override and restores the old code/venv entrypoint. Shared data is preserved; never overwrite newer customer writes with the pre-release backup.

After connecting to the known instance, snapshot current data with the app stopped, then disable the exact release drop-in:

```bash
sudo systemctl stop demo-studio
rollback_stamp=$(date -u +%Y%m%dT%H%M%SZ)
rollback_dir=/opt/demo-studio-backups/20260923-creta-v8
(umask 077; tar -czf "$rollback_dir/data-before-rollback-$rollback_stamp.tar.gz" -C /opt/demo-studio data)
sudo mv /etc/systemd/system/demo-studio.service.d/90-release-20260923.conf "$rollback_dir/90-release-20260923.conf.disabled-$rollback_stamp"
sudo systemctl daemon-reload
sudo systemctl start demo-studio
curl --fail --connect-timeout 2 --max-time 10 http://127.0.0.1:8877/api/health
```

Confirm the effective working directory and executable point to `/opt/demo-studio`, then inspect existing demos. Use a full data restore only as a separate, reviewed recovery action after preserving and reconciling post-deployment writes. Caddy needs no change for this rollback.
